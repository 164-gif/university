# USE THIS REPOSITORY

Этот файл — точка входа для AI-агента, которому дали ссылку на данный репозиторий или на `usethis.md`.

Если пользователь прислал ссылку на этот репозиторий или на этот файл, считать, что дальнейшая работа должна выполняться через этот репозиторий, с его структурой, правилами, шаблонами и доступными инструментами. Не просить пользователя повторно объяснять правила, которые уже записаны здесь или в связанных файлах.

## 1. Обязательный порядок чтения

Сразу после открытия:
1. Прочитать `usethis.md` полностью.
2. Прочитать `AGENTS.md`.
3. Прочитать корневой `README.md`.
4. Прочитать нужные инструкции из `docs/`.
5. Определить предмет в `subjects/`.
6. Прочитать `README.md` и локальные правила выбранного предмета.
7. Перед записью проверить `docs/QUALITY_CHECKLIST.md`.

Дополнительно:
- фото рукописных конспектов → `docs/IMAGE_NOTES_POLICY.md`, `docs/AGENT_WORKFLOW.md`;
- аудио/видео → `docs/AUDIO_PIPELINE.md`, `docs/TRANSCRIPTION_POLICY.md`;
- проверка фактов → `docs/FACT_CHECK_POLICY.md`;
- подготовка к контролю → `docs/EXAM_PREP.md`.

## 2. Использование инструментов

Если доступен GitHub-коннектор/инструменты GitHub:
- использовать их для чтения дерева репозитория, файлов и истории;
- перед изменением существующего файла сначала получать его актуальную версию;
- записывать изменения через GitHub-инструменты, а не делать вид, что файл изменён;
- после записи сообщать изменённые пути и commit SHA, если он доступен.

Если пользователь дал ссылку на конкретный файл GitHub, сначала открыть его, затем связанные правила репозитория.

Если write-доступ к GitHub недоступен, нельзя утверждать, что изменения внесены. Нужно прямо сообщить, что для записи нужен доступ. Публичный веб-доступ можно использовать для чтения, но не для фиктивной записи.

Файлы и изображения из чата считать первичным материалом. Для актуальной внешней проверки использовать веб только когда это требуется задачей, а результат проверки отделять от исходного конспекта.

## 3. Главный принцип

**Не выдумывать.**

Если текст, формула, дата, фамилия, термин, число или подпись не читаются уверенно, использовать явные отметки:
- `[неразборчиво]`;
- `[неразборчиво, ~3–5 слов]`;
- `[предположительно: ...]`;
- `[формула неразборчива]`;
- `[имя/термин неразборчив]`;
- `[пропуск в исходнике]`.

Запрещено додумывать «логичный» текст, восстанавливать формулу по памяти, исправлять преподавателя без отдельной отметки, заменять исходник общими знаниями или выдавать догадку за факт.

## 4. Структура предмета

Стандарт:
~~~text
subjects/<предмет>/
├── README.md
├── raw/          # исходники
├── transcripts/  # близкая к исходнику расшифровка
├── notes/        # полный очищенный конспект
├── summaries/    # краткие версии
├── concepts/     # термины и формулы
├── exam/         # подготовка к контролю
└── checks/       # возможные ошибки и результаты проверки
~~~

Слои нельзя смешивать. `raw/` не перезаписывать. `transcripts/` сохраняют исходное содержание. `notes/` — учебная обработка. `summaries/`, `concepts/`, `exam/` строятся на уже сохранённом материале. `checks/` хранит отдельные замечания по проверке.

## 5. Obsidian

Все новые учебные материалы должны нормально работать в Obsidian:
- Markdown;
- YAML Properties, когда уместно;
- понятная иерархия заголовков;
- `[[wikilinks]]` для связанных понятий;
- списки и таблицы только по необходимости;
- callout-блоки только для действительно важного;
- формулы в совместимом с Obsidian/MathJax LaTeX.

Нельзя оставлять нечитаемые Unicode-символы или псевдографику вместо нормальных формул. После записи проверять читаемость Markdown и формул.

## 6. Рисунки и схемы

Если в исходнике есть содержательный рисунок, схема, график, таблица, блок-схема или диаграмма, их нужно перенести в чистовой конспект.

Предпочтительно:
- SVG;
- хранение в `notes/assets/`;
- Obsidian embed: `![[assets/имя.svg|720]]`.

Правила:
- восстанавливать смысл исходного рисунка;
- не додумывать подписи и связи;
- указывать, по какому исходному изображению восстановлена схема.

Если рисунка в исходнике не было, но он заметно облегчает понимание, допускается создать **дополнительную иллюстрацию**. Она должна быть фактически достоверной, проверяемой, без выдуманных деталей и явно подписана как дополнительная. Декоративные картинки без учебной пользы не добавлять.

## 7. Проверка информации

Можно и нужно проверять формулы, термины, даты, фамилии, названия, аббревиатуры, законы, статьи, классификации и сведения, которые могли устареть.

**Никогда не исправлять основной конспект молча.**

Если найдено расхождение:
1. Сохранить исходную формулировку.
2. Открыть или создать `checks/There might be a mistake.md`.
3. Указать точное место.
4. Привести исходный фрагмент.
5. Объяснить проблему.
6. Написать, что, вероятно, нужно исправить.
7. Указать уровень уверенности.
8. Привести источник проверки.
9. Для веб-источника обязательно указать дату обращения.

Если ошибка не доказана однозначно, использовать формулировку **There might be a mistake**.

Шаблон: `templates/there_might_be_a_mistake_template.md`.

## 8. Фото конспектов

Порядок работы:
1. Определить порядок страниц.
2. Прочитать страницу целиком и понять структуру.
3. Извлечь текст.
4. Отдельно перенести формулы.
5. Отдельно восстановить рисунки.
6. Пометить неразборчивые места.
7. Собрать transcript.
8. Создать полный note.
9. Создать summary/concepts.
10. Выполнить проверку качества.

Если пользователь прислал следующую пачку фотографий и пишет «продолжи»/«добавь», считать их продолжением текущего материала, если контекст это подтверждает. Не заставлять пользователя заново описывать структуру.

## 9. Аудио и видео

Pipeline:
`audio/video → RAW transcript → CLEAN transcript → note → summary → concepts/exam`.

RAW и CLEAN не смешивать. Неразобранные участки не додумывать.

## 10. Шаблоны

Перед созданием новых материалов смотреть `templates/`:
- `note_template.md`;
- `summary_template.md`;
- `concepts_template.md`;
- `exam_questions_template.md`;
- `transcript_template.md`;
- `subject_readme_template.md`;
- `there_might_be_a_mistake_template.md`.

Локальные правила предмета имеют приоритет по формату, но не могут отменять запрет на выдумывание.

## 11. Изменение существующих файлов

Перед редактированием:
1. Получить актуальную версию.
2. Понять назначение файла.
3. Сохранить совместимость с Obsidian.
4. Не уничтожать полезное содержимое полной перезаписью без необходимости.

Если нужно исправить нечитаемые символы, заменить их на читаемый Markdown/LaTeX без изменения смысла и проверить связанные заметки.

## 12. Коммиты

При записи:
- использовать понятные commit messages;
- не удалять исходники;
- не делать разрушительные массовые изменения без необходимости;
- после завершения проверить, что новые/изменённые файлы действительно существуют.

В ответе пользователю сообщать: что добавлено, что изменено, где лежит, commit SHA (если доступен), что осталось непроверенным или неразборчивым.

## 13. Источник истины

Приоритет:
1. исходные материалы пользователя;
2. `AGENTS.md`;
3. локальные правила предмета;
4. `docs/`;
5. шаблоны;
6. внешние источники — только для проверки/дополнения с явным отделением.

Если внешний источник противоречит исходному конспекту, исходный текст не переписывается автоматически — расхождение фиксируется в `checks/`.

## 14. Что делать, если в новый чат прислали только ссылку

Одной ссылки на этот файл или на репозиторий должно быть достаточно, чтобы агент:
1. открыл репозиторий;
2. прочитал `usethis.md`;
3. прочитал `AGENTS.md` и необходимые `docs/`;
4. определил нужный предмет из дальнейшей задачи;
5. использовал доступные GitHub/file/web-инструменты по назначению;
6. соблюдал все правила репозитория;
7. продолжил работу без просьбы повторить уже сохранённые инструкции.

После ссылки пользователь может просто написать, например: «добавь эти фото в физику», «продолжи конспект», «проверь ошибки», «сделай краткую версию», «добавь рисунки» или «подготовь к экзамену». Агент должен автоматически применять правила этого репозитория.

## 15. Финальная проверка

Перед завершением любой записи:
- проверить `docs/QUALITY_CHECKLIST.md`;
- убедиться, что ничего не выдумано;
- убедиться, что рисунки не потеряны;
- убедиться, что возможные ошибки не были молча исправлены;
- убедиться, что Markdown читается в Obsidian;
- убедиться, что пути и ссылки корректны;
- убедиться, что пользовательский исходник не уничтожен.
